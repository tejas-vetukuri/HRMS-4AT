# HRMS (Django) — Task Breakdown

**Sources:** [`IMPLEMENTATION-PLAN.md`](IMPLEMENTATION-PLAN.md) (the phase plan) and its
review; a separate HRMS Product Requirement & System Architecture (PASA) gap-analysis
document (not reproduced in this repo) — specifically its gap analysis checked against
a previously-running system, for scope and priority, and its full aspirational product
catalogue for context only, not adopted wholesale — see the note below the table on
scope decisions, and the conflicts section in [README.md](README.md).

**Legend:** `E1` Lead/Core · `E2` Core Apps · `E3` Features · `E4` Infra/Payroll · `SH`
shared/no-single-owner task. `⛓` marks a task that is blocked by, or waiting on, another
engineer's task — read it before starting so you don't build against a shape that's
still moving. `[gap]` marks a task that was not in the original phase plan — it was
added from the plan review (missing fallback paths, missing security controls, an
incorrect start-date calendar, a validated-but-missing feature from the PASA gap
analysis) so it doesn't silently get dropped during execution.

**Task #** is a code in the form `P{phase}-{engineer}-{seq}`, e.g. `P2-E2-02` = Phase 2,
E2, 2nd task in that section — the engineer letter tells you who owns it, since the
table no longer groups rows under a subheading. **Dependency** names the exact upstream
task ID(s) and, in parentheses, the specific model/endpoint/helper that task creates —
not just "Phase X" in the abstract. **None** means the task needs nothing else in this
plan and can start as soon as its phase opens.

**On permissions and role-based access:** the PASA document describes two different
RBAC models, and this plan deliberately follows only one of them. The real,
already-running system's ADR-001 uses a two-axis model — permission codes for "what
kind of action" plus a separately-resolved scope ("on whom": self / team / org-wide via
`scope.all`) — and dot-notation permission codes (`leave.approve`, `expense.write`).
Phase 1 here follows that same permission-code convention (`P1-E1-03`) and the same
two-axis shape in spirit, simplified to what MVP actually needs:
`core/scope.py::visible_employee_ids()` (`P1-E1-05`) gives self + direct reports, with
`hr_admin`/`finance` roles getting org-wide reach through the role check itself rather
than a separate `scope.all` permission — there's no `manager_scopes` table or
team/department scope tier, because MVP has exactly 4 flat roles, not the arbitrary
custom-role assignment the two-axis model exists to support. The PASA's full role
catalogue (15 named admin roles — Global Admin, HR Manager, Payroll Manager,
Attendance Admin, etc. — plus AND/OR scope logic, confidential-folder permissions, IP
whitelisting, 2FA) is the full enterprise product vision, explicitly checked *against*
a codebase rather than written *for* this one, and isn't adopted here — it would
directly contradict the Implementation Plan's "4 roles for MVP" decision. If the
product later needs more than 4 roles, `P1-E1-01`'s `Role`/`Permission`/`RolePermission`
tables extend cleanly to that; nothing here forecloses it.

## Phase 1 — Core: Identity, RBAC, Auth (4 days: Sep 21 Mon – Sep 24 Thu)

⚠ **This is the highest-risk phase in the entire plan.** The `core/scope.py` filter
being built here is the direct fix for a confirmed, live IDOR vulnerability (any
employee could previously read any other employee's data by changing an ID in a URL).
Nothing in this phase merges on one engineer's own say-so — see the mandatory review
task below.

| Task # | Task | Dependency |
|---|---|---|
| `P1-E1-01` | **Build the `accounts` app's core models.** Create `User`, `Role`, `Permission`, and `RolePermission` with a migration. `User` should carry a direct foreign key to `Role` (see the next task for why this matters), `Permission` stores enumerated permission strings, and `RolePermission` maps which permissions each role holds. | `P0-E1-03` (Core app skeletons) |
| `P1-E1-02` | **Confirm `User → Role` is a direct foreign key, not a many-to-many relationship.** The plan specifies "single role per user for MVP" — if this were implemented as an M2M through a `user_roles` join table, a user could silently end up with two roles with no error, and downstream code that assumes one role would pick one arbitrarily. A direct FK makes "one role per user" a database constraint instead of a convention someone has to remember to honor. | `P1-E1-01` (`accounts` app core models) |
| `P1-E1-03` | **Seed the 4 MVP roles and their permission strings via a data migration or management command.** Employee, Manager, HR Admin, and Finance, each granted the enumerated permission strings the plan calls for. **[gap] Use dot-notation for every permission code** (`leave.approve`, `expense.write`, `attendance.read.self`, `attendance.read.team`, `scope.all`, etc.), not colon-notation — this matches the convention already in use elsewhere in the product, and getting it right now avoids a rename across every `@RequirePermissions`-equivalent decorator once Phase 2+ modules start declaring their own codes. | `P1-E1-09` | **Make `GET /users/me` match the frontend contract exactly.** Response shape: `roles` is an array containing exactly one object (`[{name}]`), `permissions` is a flat array of permission strings, and there is no `scope` field in the response at all (the frontend doesn't expect one and dropping it was a deliberate contract decision, not an oversight). | `P1-E1-06` (Auth endpoints (`simplejwt`)); `P1-E1-03` (Seed 4 MVP roles + dot-notation permission strings) |
